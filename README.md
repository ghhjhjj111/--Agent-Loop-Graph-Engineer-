# 闪学it-慕课-Agent Loop + Graph Engineer 工程化实战
Agent Loop + Graph Engineer 工程化实战复盘：智能体循环与图工程高频踩坑指南

参加完 Agent Loop + Graph Engineer 工程化实战营，我最大的感受是：智能体不是“接上大模型就能跑”，图工程也不是“画几个节点连起来就完事”。我们小组在两周里搭了三套工作流，踩的坑几乎覆盖了从设计到上线的全链路。复盘下来，真正拖垮项目的往往不是模型不够强，而是工程化细节没做好。

第一个坑：把循环当成自动跑，没有终止条件。
刚开始我们让智能体“一直思考直到解决问题”，结果它反复调用同一个工具，把同一份数据查了十几遍，token 烧得飞快，任务却没进展。Agent Loop 的核心不是无限循环，而是有感知、有规划、有行动、有观察、有退出。避坑方法：设置最大步数、超时时间、预算上限和明确的终止条件。比如连续两次观察结果无变化，就强制退出并转人工。循环要有闸，不能让它自己跑飞。

第二个坑：图设计成蜘蛛网，节点职责不清。
我们一开始追求“全自动”，把意图识别、检索、推理、工具调用、审核全塞进一张图，条件边越连越多，最后连自己都看不懂。调试时一个分支出错，整张图跟着崩。避坑方法：一个节点只做一件事，先跑通线性流程，再按需加分支。路由条件必须显式、可解释，边要有命名规范。图不是越复杂越智能，而是越清晰越可靠。

第三个坑：状态管理混乱，上下文越跑越脏。
智能体每轮都把全部历史塞进提示词，结果上下文膨胀，模型开始遗忘关键信息，甚至把之前的错误结论当事实。更糟的是，多个分支共享状态时互相污染。避坑方法：设计显式状态结构，区分短期记忆和长期记忆，用摘要压缩历史，把事实存到外部存储。每个会话隔离状态，定期清理过期信息。状态有账，智能体才不会精神分裂。

第四个坑：工具调用没有契约，失败重试变灾难。
我们对接了一个订单查询工具，返回格式时好时坏，异常也没分类。智能体遇到失败就重试，结果重复提交了三次订单。避坑方法：为每个工具定义清晰的输入输出契约，保证幂等性，设置超时、退避和熔断。错误要分类：可重试的、不可重试的、需要人工的。工具有约，循环才不会闯祸。

第五个坑：可观测性不足，出问题只能靠猜。
上线后用户反馈“结果不对”，我们却不知道是哪一步出的错。没有日志、没有追踪、没有回放，只能凭感觉改提示词。避坑方法：全链路记录每一步的输入、输出、耗时和成本，给每次运行生成唯一追踪标识。建立回放机制，把失败案例变成评估样本。链路有眼，优化才有方向。

第六个坑：评估靠感觉，上线就翻车。
我们只测了顺利场景，觉得效果不错就上线。结果遇到模糊指令、工具超时、多轮追问，智能体立刻露馅。避坑方法：构建覆盖边界和对抗场景的评估集，离线跑分，灰度发布，A/B 对比。人工评审不能省，尤其是高风险任务。评估有据，才敢说“能上线”。

第七个坑：过度工程化，为了图而图。
课程后期，我们试图把每个想法都做成节点，结果维护成本极高，改一处要动十处。避坑方法：保持最小可行图，能线性就不分支，能单节点就不拆多节点。先解决业务问题，再谈架构优雅。图是骨架，不是炫技。

复盘到最后，我们总结出一句口诀：循环有闸，图有边界，状态有账，工具有约，链路有眼，评估有据，人工有兜。 Agent Loop 是心跳，Graph Engineer 是骨架，工程化才是保险。智能体不是魔法，而是一套需要被约束、被观测、被迭代的系统。避开这些坑，智能体才能真正从演示走向生产。
